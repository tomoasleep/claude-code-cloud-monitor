claude-code-cloud-monitor（cccm）詳細設計

Claude Code のクラウドセッションを手元の CLI から起動・監視するための OSS。第 7 版（2026-11-25、起動方式の決定を反映）。決定済み は tomoasleep の合意があるもの、未決 は「未決の事項」で聞くもの、検証済み はクラウドで試して確かめたもの、第 N 版で変更 はその版で変えたところ。

第 7 版の主な変更（tomoasleep の決定、2026-11-25「変に賢く振る舞わないようにする。基本的に routine を使うか api scheduled task を使うかもユーザーに指定させるし、うまく設定できてなかったら ack できなくて失敗するのも許容する」）

  • 起動方式を cccm launch --via cloud|routine でユーザーが指定する。cccm は自動で選ばない。routine は routine（scheduled task）の fire API を呼ぶ（5 章）。
  • hub の repo が作業 repo と違うかを cccm が判定して add_repo の指示を足すのはやめた。repo の紐づけ（routine の repo、プロンプトでの指示、環境の許可）はユーザーが用意する。足りなければ ack が来ず、--ack-timeout で失敗する（4 章、9.2）。
  • cccm plugin install は mcp__claude-code-remote__add_repo を許可に足さない（cccm が add_repo を使わなくなったため）。
  • VM の settings.json で許可しても、add_repo が claude.ai 側の承認を求めるようになったことを確かめた（2 章）。

第 6 版の主な変更（5 回目の注釈 2 件）

  • herdr-symphony のテストの作りと書き方（deps の注入、CommandRunner、待ちの 1 歩ずつの実行、時計の注入、引数の純粋関数、runCli、Docker の e2e）を取り入れた（10 章）。
  • gh を環境変数で emulate に向けられることを確かめた（GH_HOST=github.localhost と HTTP_PROXY）。本番は gh api のまま（10 章）。
  • テストも Node。

第 5 版の主な変更（4 回目の注釈 1 件）

  • テストを herdr-symphony の構成に揃え、GitHub と LLM を vercel-labs/emulate で置き換える 4 層にした（10 章）。GitHub の呼び方（Q4）とテストの実行環境（Q5）を聞く。

第 4 版の主な変更（3 回目の注釈 4 件）

  • 送り先は cccm report init --to … で 1 回だけ設定し、init が ack を兼ねる。以後のコマンドと hook は --to なしで同じ先に書く。プロンプトの印はやめた（4 章、6 章）。
  • リマインダを受けて作業を続けるときも pending を送らせ、リマインダをいったん止める（4 章）。
  • コメントは「## 直近の応答」の見出しの下を <details> で畳む（7 章）。
  • 例に出していた私的な repo の名前は仮の名前なので、<hub-owner>/<hub-repo> に置き換えた。

第 3 版の主な変更

  • VM への導入の 3 項目をクラウドで検証した（8 章）。setup script で入れた plugin の hook は発火し、Bash(cccm report:*) は承認なしで通った。
  • リマインダを herdr-symphony に揃えた。報告の状態は done / pending / failed。起動直後 3 分は送らない、pending は 15 分ごとに再送、回数の上限は設けず --timeout で止める（4 章）。
  • hook がターンの終わり（Stop）を書くので、done が来ないことは自動で検知してリマインダを送れる、と比較に書き直した（9.1）。
  • Rate Limit: Issue の events API にはコメントの編集が出ないため使えない。代わりに ETag の条件付きリクエスト（304 は rate limit を消費しない）と、repo 全体のコメント一覧（sort=updated&since=）でまとめて読む（4 章、9.4）。
  • コメントの「直近の返答」は <details> に入れる（7 章）。

第 2 版の主な変更

  • CLI の引数を claude の CLI に寄せた。cccm 固有でないオプションは claude --cloud にそのまま渡す。
  • クラウド側にも cccm を入れ、エージェントが cccm report ack / cccm report done を明示的に実行する。hook も cccm report hook を呼ぶだけにする（Node）。
  • launch はターンの終わりでは止めず、done が来るまで待つ。done なしでターンが終わったら、claude -p "…" --cloud <id> --output-format json でリマインダを送る。
  • 後から監視を始める attach は今回やらない（やるなら cccm attach）。

1. 目的

手元の CLI から Claude Code のクラウドセッション（claude.ai/code）を起動し、そのセッションのタスクが終わったこと（done）・途中の TODO・最後の報告を受け取れるようにする。herdr-symphony などのツールが JSON で使える形にする。

終わりの状態: 次のコマンドが動き、README の手順だけで他の人が使える。

  • 手元: cccm launch（claude --cloud を包んで起動し、done まで待つ）、cccm monitor（起動済みのセッションを同じように待つ）、cccm plugin install（VM に hook を入れる）。
  • クラウド: cccm report init|progress|pending|done|failed|hook（hub に状態を書く）。

2. 制約

変えられない前提（外部の仕様・実験で確かめた事実）

事実根拠
新しいセッションの作成は対話の起動だけ。claude -p … --cloud は「--cloud cannot be combined with --print」で拒否される。--output-format json を付けても作成時の出力はテキスト（Created cloud session / View: <URL>）のまま。TTY がないと起動しないので script を使う。実験（2026-11-25、claude 2.1.331）
既存のセッションへの送信は claude -p "msg" --cloud <id> --output-format json で TTY なしにでき、{"ok":true,"session_id":…,"url":…} が返る。実験（2026-11-24）
環境は --settings <file> の remote.defaultEnvironmentId で起動ごとに選べる。--environment は自前の環境（ccpool_）専用。実験（2026-11-25）、anthropics/claude-code#111691
--cloud で紐づく repo は cwd の repo 1 つだけ。実験（2026-11-25）、docs
クラウドから GitHub の REST が通るのは、セッションに紐づいた repo だけ。GraphQL は通らない。実験（2026-11-24）
セッションの中で add_repo を使うと repo を足せる。第 7 版で変更 午前の実験では VM の ~/.claude/settings.json の permissions.allow に入れれば承認なしで通ったが、同じ日の午後には、同じ setup script（cccm を入れる前のもの）でも「This connector call requires your approval to proceed.」で承認待ちになった（VM の claude 2.1.332）。起動フラグの権限は VM に届かない。実験（2026-11-25）
第 7 版で追加 routine（scheduled task）は定義の job_config.ccr.session_context.sources に repo を複数入れられ、起動したセッションには最初から全部が clone され、add_repo なしで hub の Issue に書けた。実験（2026-11-25）
第 7 版で追加 routine の fire API: POST https://api.anthropic.com/v1/claude_code/routines/{trig_id}/fire、ヘッダーは Authorization: Bearer <routine ごとの token>（sk-ant-oat01-、画面で発行し一度しか表示されない）・anthropic-version・Content-Type: application/json。body は text（最大 65,536 文字）だけ。応答は {"type":"routine_fire","claude_code_session_id":"session_…","claude_code_session_url":"…"}。text は保存したプロンプトの後ろに <routine-fire-payload> としてデータ扱いで届くので、保存するプロンプトに「payload のタスクを実行する」と書く必要がある。上限は routine ごとに 1 時間 30 回、アカウントの API fire が 1 時間 100 回。冪等キーはない。experimental。docs（platform.claude.com の routines-fire）、実験（2026-11-25）
hook はクラウドでも発火し、紐づいた repo の Issue のコメントを REST の PATCH で書き換えられた。実験（2026-11-25）
CLAUDE_CODE_REMOTE_SESSION_ID（cse_…）は Bash と hook の両方で読め、先頭を session_ に替えると claude.ai の URL になる。CLAUDE_CODE_REMOTE=true はクラウドでだけ立つ。実験（2026-11-25）

決定済み（tomoasleep、2026-11-25、チャットと Plannotator）

  • public の tomoasleep/claude-code-cloud-monitor。社内・私的な repo や組織の名前は入れない。
  • TypeScript、実行時の依存なし、npm で配る（bin は cccm）。hook も Node。
  • hook は Claude Code plugin として配り、cccm plugin install で導入する。PostToolUse は全ツールにはかけない。
  • CLI は claude の CLI に寄せる（追加するオプション以外）。
  • ack はエージェントに明示的に行わせる。ack が 5 分以内に来なければ失敗。第 7 版で変更 hub の repo をセッションに紐づけるのはユーザーの責任で、cccm は推測して指示を足さない。
  • 第 7 版で追加 起動方式（claude --cloud か routine の fire か）はユーザーが指定する。設定が足りずに ack が来ず失敗するのは許容する。
  • launch は done が来るまで止めない。done なしでターンが終わったら、リマインダを送る（herdr-symphony と同様）。
  • attach（cccm が起動していないセッションの監視）は今回やらない。

3. 過去の検討

探した場所: 手元の実験の記録、以前に私的な repo で作った状態報告の hook、getty104/claude-task-worker、anthropics/claude-code の Issue、第 1 版への注釈。

  • claude-task-worker: エージェントに最後の操作でラベルを付けさせ、手元が poll する。4 時間で打ち切り。cccm は「エージェントの明示的な報告（ack / done）」と「hook の自動の報告（ターンの終わり・TODO）」を組み合わせ、done が来ないときはリマインダで促す点が違う。
  • 第 1 版: hook だけで報告し、最初のターンの終わりで launch を止める案だった。ターンの終わりはタスクの完了を意味しない（質問で止まる場合もある）ため、明示的な done に変えた。

4. 全体の流れ 第 2 版で変更

  1. hub を用意: 手元の gh で hub の Issue に状態のコメントを 1 つ作る（状態 launching）。
  2. プロンプトを組み立てる: ユーザーのプロンプトを先頭に置き（スラッシュコマンドを Skill として起動させるため）、後ろに cccm の指示を足す（下の「エージェントへの指示」）。
  3. 起動 第 7 版で変更: --via で指定した方式で起動する。
    • --via cloud: script 経由で claude --cloud <prompt> [渡されたオプション]。出力からセッション ID と URL を取る。--env があれば --settings の一時ファイルで渡す。紐づく repo は cwd の repo だけ。
    • --via routine: routine の fire API に、組み立てたプロンプトを text として送る。応答の claude_code_session_id をセッション ID にする。repo・環境・権限は routine の定義で決まり、cccm は触らない。
  4. ack を待つ: エージェントが cccm report init を実行し、状態に acked_at が入るのを待つ。--ack-timeout（既定 5 分）を過ぎたら失敗。
  5. done を待つ 第 3 版で変更: コメントを poll（既定 10 秒ごと、ETag の条件付きリクエスト）。途中経過（TODO、progress、ターンの終わり）を出力する。
    • done または failed が来たら、最終の報告を出して終わる。
    • 報告なしでターンが終わった（hook が turn_ended を書いた）ら、claude -p "<リマインダ>" --cloud <id> --output-format json でリマインダを送る。ただし起動から --reminder-grace（既定 3 分）の間は送らない。
    • pending が報告されたら待ち続け、--pending-remind-interval（既定 15 分）ごとにリマインダを再送する。
    • 回数の上限は設けない。--timeout を過ぎたら失敗。

    以上は herdr-symphony の report_file 方式（done / pending / failed、reminder_grace_period_ms 3 分、pending_remind_interval_ms 15 分、idle で報告がなければリマインド）に揃えた。リマインダの送信は、2026-11-25 に claude -p … --cloud <id> --output-format json で送れること、送ったメッセージでも hook の UserPromptSubmit が発火することを確かめた。

GitHub の読み方（Rate Limit） 第 3 版で追加

  • 1 つのセッションを待つとき: そのコメントを GET /repos/{o}/{r}/issues/comments/{id} で、前回の ETag を If-None-Match に付けて読む。変わっていなければ 304 が返り、docs によれば rate limit を消費しない（「Making a conditional request does not count against your primary rate limit if a 304 response is returned」）。2026-11-25 に、15 回の 304 で残りがほぼ減らないことを確かめた（同じ token を他でも使っていたため、厳密な数ではない）。
  • 同じ hub の repo で複数のセッションを待つとき（symphony など）: GET /repos/{o}/{r}/issues/comments?sort=updated&direction=desc&since=<前回> を ETag 付きで 1 回読み、変わったコメントだけを処理する。この形の呼び出しが 200 を返すことは確かめた（引数の docs は未読）。
  • Issue の events API（/issues/events）と timeline はコメントの編集を出さないので使わない（docs に編集のイベントがない）。
  • クラウド側の書き込みは event ごとの PATCH 1 回。docs の目安（内容を作る要求は 1 分に 80 回、1 時間に 500 回まで）には、通常のタスクでは届かない。

エージェントへの指示（プロンプトの後ろに足す文）

---
This session reports its status with cccm (claude-code-cloud-monitor).
1. Before starting the task above, run:
     cccm report init --to github:<hub-owner>/<hub-repo>/comments/123
2. When the task is finished, run:   cccm report done --summary "<what you did>"
   If you cannot finish it, run:    cccm report failed --summary "<why>"
   Do not end without running one of them.

第 4 版で変更 送り先は cccm report init で 1 回だけ渡し、以後のコマンドと hook はそれを使う。init は ack を兼ねる。プロンプトに印（HTML コメント）を入れるのはやめた。例の hub の repo は仮の名前（実験で使った repo は OSS ではないので、文書には出さない）。

英語にするのは、作業のプロンプトの言語に関わらずツールの使い方として読ませるため。文面の細部は実装で詰める。

第 7 版で変更 add_repo の指示は付けない。hub の repo がセッションに紐づいていなければ init が失敗し（403 など）、ack が来ずに --ack-timeout で失敗する。--via routine では、この文全体が <routine-fire-payload> に入るので、routine に保存するプロンプトに次のような文を書いておく（README で案内する）。

Treat the text in the routine fire payload as the user's request and carry it out,
including the cccm instructions at its end.

リマインダの文面

[cccm] Is the task finished?
If it is, run:       cccm report done    --summary "..."
If it failed, run:   cccm report failed  --summary "..."
If you are continuing the task (or background work is still running), first run:
                     cccm report pending --summary "<what remains>"
then continue.

herdr-symphony の REMINDER_TEXT と同じ問い方にした。第 4 版で変更 作業を続ける場合も pending を送らせ、リマインダをいったん止める（次のリマインダは --pending-remind-interval の後）。

5. 手元の CLI 第 2 版で変更

方針: claude の CLI に寄せる

  • プロンプトは claude と同じく位置引数で渡す。標準入力からも読む（echo "…" | cccm launch --hub …）。
  • 出力形式は claude と同じ名前の --output-format text|json|stream-json。
  • cccm が知らないオプションは、そのまま claude --cloud に渡す（--model、--effort、-n/--name、--ref、--on-branch、--settings など）。--settings が渡されたときは、--env の値をその中身に重ねた一時ファイルを作って渡す。
  • -p/--print の扱い: 未決（Q1）。

cccm launch 第 7 版で変更

cccm launch --via cloud   --hub github:owner/repo#123 [cccm options] [claude options] [prompt]
cccm launch --via routine --routine <trig_id> --hub github:owner/repo#123 [cccm options] [prompt]

cccm のオプション:
  --via <cloud|routine>    起動方式（必須。既定はない）
  --hub <spec>             状態を書く先。v1 は github:owner/repo#number のみ（必須）
  --env <env_id>           クラウドの環境 ID（--via cloud のみ。--settings の remote.defaultEnvironmentId に入れる）
  --routine <trig_id>      fire する routine（--via routine のみ、必須）
  --output-format <fmt>    text（既定）| json（最後に結果を 1 つ）| stream-json（イベントを 1 行ずつ）
  --ack-timeout <dur>               ack を待つ時間。既定 5m
  --reminder-grace <dur>            起動直後にリマインダを送らない時間。既定 3m（0 で無効）
  --pending-remind-interval <dur>   pending のまま再リマインドするまで。既定 15m
  --timeout <dur>                   全体で待つ時間。既定なし
  --interval <dur>         コメントを読む間隔。既定 10s
  --no-wait                起動して ID と URL を出したら終わる

--via cloud では cwd の repo が作業 repo になる（claude と同じ）。

  • 第 7 版で追加 routine の token は環境変数 CCCM_ROUTINE_TOKEN で受け取る（引数にすると shell の履歴やプロセス一覧に残るため）。token は routine ごとなので、複数の routine を使う呼び出し側（symphony など）は呼び出しごとに環境変数を替える。--via routine で token がなければ引数の誤り（終了コード 2）。
  • --via routine では --env と claude に渡すオプション（--model など）は使えない（routine の定義で決まるため）。渡されたら引数の誤り。
  • fire が 2xx 以外を返したら、応答の error.message を出して終了コード 5。fire は冪等でないので、cccm は再試行しない。
  • リマインダは --via に関わらず claude -p … --cloud <session_id> で送る（routine のセッションに送れるかは通し確認で確かめる）。

cccm monitor

cccm monitor --hub github:owner/repo#123 [--session <id>] [options]

  --session <id>   監視するセッション。省略時は Issue の中で最も新しい cccm のコメント
  --ack-timeout / --reminder-grace / --pending-remind-interval / --timeout / --interval / --output-format は launch と同じ

launch の「起動」より後ろ（ack を待つ・done を待つ・リマインダ）と同じ処理。launch を --no-wait で起動した後に使う、または launch が途中で止められたときに続きを待つために使う。

{"type":"ack","at":"…"}
{"type":"progress","tasks":[{"subject":"Write tests","done":true}],"message":"…"}

終了コード

1failed
2引数の誤り
3ack が来なかった

6. クラウド側の cccm report 第 2 版で追加

cccm report init     --to <ref>        送り先を設定し、ack を書く
cccm report progress "<message>"
cccm report pending  [--summary "…"]
cccm report done     [--summary "…" | --summary-file <path>]
cccm report failed   [--summary "…" | --summary-file <path>]
cccm report hook     （hook から呼ぶ。標準入力の hook の JSON を読む）
  • 第 4 版で変更 init の --to（github:owner/repo/comments/123）を状態ファイルに保存し、同時に ack を書く。以後の report と hook は、状態ファイルの送り先に書く。init の前に起きた hook の event は書かない（送り先がないため）。--to を他のコマンドに付けたときは、その送り先を優先する。
  • どのコマンドも、コメントの状態を読んで更新し、全体を書き直す（gh api -X PATCH）。状態ファイル /tmp/cccm/<CLAUDE_CODE_REMOTE_SESSION_ID>.json を手元の写しとして持ち、コメントを読めないときもそこから書く。
  • report hook の event: UserPromptSubmit（turn を 1 増やす）、TaskCreated / TaskCompleted（TODO）、Stop（turn_ended と last_message）。CLAUDE_CODE_REMOTE が true でなければ、または init されていなければ何もしない。失敗しても exit 0、標準出力には何も出さない。
  • report init / done / failed / pending は、エージェントが結果を見られるよう、失敗したら exit 1 と理由を出す（hub の repo を足し忘れた 403 など）。

GitHub を emulate に向ける方法 検証済み

tomoasleep の注釈「環境変数とかで差し替えられない？」を受けて、手元で試した（2026-11-25、gh 2.105.0、emulate 0.14.0）。

  • GH_HOST=github.localhost にすると、gh は http://api.github.localhost/… を HTTP で呼ぶ（/api/v3 は付かない）。他のホスト名だと HTTPS と /api/v3 になる。
  • emulate を任意のポートで起動し、HTTP_PROXY=http://127.0.0.1:<port> を足すと、その要求が emulate に届く。GH_TOKEN には emulate の seed の token を入れる。
  • これで gh api による Issue の作成、コメントの作成、PATCH、1 件の取得、Issue ごとの一覧が emulate で通った。本番のコードは gh api のままでよく、テストは環境変数だけで切り替えられる。
  • emulate で試せないもの: repo 全体のコメント一覧（/repos/{o}/{r}/issues/comments）は 404 が返った（Issue の番号の経路と衝突しているように見える）。ETag のヘッダーも返らない。この 2 つは CommandRunner の偽物で単体テストする。

どのテストでも、置き換えるのは外部入出力（GitHub、LLM、claude と script の起動）だけにする。テストは Node（node --test）で書く（tomoasleep の回答、2026-11-25）。

第 2 版で聞いたこと（記録）

Q1. -p をどう扱うか

claude では -p/--print が「対話なしで実行して結果を出す」。cccm launch は常に対話なしなので、-p は意味を持たない。claude に寄せるなら、-p を受け付けて無視するか、cccm を launch なしで cccm -p "…" --hub … と呼べる形にする手もある。

  • cccm launch [prompt] のみ。-p は受け付けない
  • cccm launch -p "…" も受け付ける（-p の値をプロンプトとして扱う）
  • cccm -p "…" --hub … で launch と同じ動きにする（claude と同じ呼び方）

推奨: cccm launch [prompt] のみ。サブコマンドが複数あるので、launch を明示するほうが読み違えがない。

Q2. リマインダの既定値

ターンが終わってから送るまでの時間と、送る回数の上限。短すぎると、エージェントが自分で続けるターンと重なる。

  • 1 分後、3 回まで
  • 3 分後、5 回まで

推奨: 1 分後、3 回まで（送る前に、次のターンが始まっていないかを状態で確かめる）。

Q3. 手元から送るリマインダ以外の操作

同じ送信の仕組みで、手元から追加の指示を送る cccm send --hub … "<message>" も作れる。claude の -p --cloud <id> を直接使えば済むので、v1 には入れない案。

  • v1 には入れない
  • v1 で cccm send を入れる

推奨: v1 には入れない。
